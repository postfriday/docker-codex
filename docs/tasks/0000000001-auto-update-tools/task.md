## Цель

Настроить GitHub Actions так, чтобы при появлении новой стабильной версии Codex, OpenCode или Claude Code автоматически обновлялся Dockerfile, увеличивалась patch-версия образа и публиковался новый образ в GHCR.

## Согласованные решения

- Выпуск полностью автоматический, без обязательного ручного подтверждения допустимых обновлений.
- Проверка обновлений выполняется каждый час.
- Patch- и minor-обновления CLI принимаются автоматически; major-обновления требуют ручного рассмотрения.
- Для нового major создаётся одна GitHub Issue на пару «инструмент + major», без повторов при почасовых проверках. Остальные CLI продолжают обновляться; для текущего major выбирается последняя стабильная версия в его пределах, даже если `latest` уже перешёл на следующий major.
- Найденные уязвимости включаются в отчёт и не блокируют выпуск.
- Перед публикацией проверяются запуск и ожидаемые версии всех трёх CLI на AMD64 и ARM64.
- Незавершённый выпуск автоматически продолжается при последующих запусках без нового бампа. До его завершения следующий автоматический релиз не начинается; ручной повтор также доступен.
- Техническая ошибка сканирования или сохранения отчёта приостанавливает выпуск; последующие запуски автоматически повторяют неудавшийся шаг.
- Собранный кандидат сохраняется в GHCR под служебным тегом. После сохранения повторы продолжаются с тем же digest, без пересборки кандидата; см. [ADR](adr.md).
- Major принимается обычным PR с изменением версии CLI в Dockerfile. После слияния автоматизация проверяет новый состав, увеличивает версию образа и выпускает его; закрытие Issue само по себе не разрешает обновление.
- После трёх неудачных попыток одного выпуска создаётся одна Issue; почасовые повторы продолжаются.
- Разрешена ручная отмена конкретного выпуска. Номер остаётся использованным, кандидат сохраняется для диагностики. Следующий выпуск допускается после изменения состава или исправления Dockerfile; отменённый состав не запускается автоматически повторно.
- Release-коммит и аннотированный git-тег создаются до сборки, резервируя номер и исходники выпуска. Наличие git-тега само по себе не означает успешную публикацию образа.
- Выпуск завершён после успешных проверок обеих архитектур, сохранения отчётов, attestation и назначения итоговых тегов образа. Повторы старого выпуска не возвращают общие теги `latest`, major и minor на старую версию.
- После принятия PR сначала выпускается точный состав из него; новые версии npm рассматриваются в следующем цикле.
- Версия CLI и версия образа — отдельные понятия: см. [глоссарий](context.md).

## Технические вопросы для реализации

- Проверить правила основной ветки и доступные права на сервере перед включением автоматизации. Не обходить защиту ветки; если она препятствует полностью автоматической записи, отдельно согласовать способ интеграции.
- Выбрать долговечное хранилище состояния выпуска, доступное между запусками. Не полагаться только на логи, cache или срок хранения artifacts GitHub Actions. Проверить восстановление состояния после сбоя между внешним действием и записью результата.
- Состояние должно связывать версию образа, git-тег и SHA, ожидаемые версии CLI, digest кандидата, результаты шагов, число неудачных попыток, Issue и факт ручной отмены. Отменённый состав должен различаться с исправленным Dockerfile даже при тех же версиях CLI.
- Проверить поддержку хранения кандидата и публикации того же многоархитектурного digest выбранными Docker/GHCR-инструментами. Частично сохранённую архитектуру нельзя считать готовым кандидатом.

## Исходные расхождения с реализацией

- Текущий workflow публикует итоговые теги до attestation и сканирования Trivy. Для проверок, блокирующих выпуск, порядок потребуется изменить.
- В текущей конфигурации Trivy не указан блокирующий `exit-code`; lint и проверки запуска CLI в workflow публикации отсутствуют.
- Повторная сборка одного git-тега может дать другой состав образа из-за незакреплённых зависимостей. Политику повторной публикации нужно определить явно.
- Проверка только новых версий не восстанавливает выпуск после сбоя между отправкой release-коммита и запуском публикации.

## Порядок обработки

1. Продолжить незавершённый выпуск, если он есть; не резервировать следующий номер.
2. Если активного выпуска нет, обработать ещё не выпущенное ручное изменение состава из принятого PR без подстановки новых версий npm.
3. Иначе проверить npm и выбрать допустимые обновления; новый major передать на рассмотрение через Issue.
4. При наличии изменений один раз увеличить patch версии образа, закрепить исходники release-коммитом и аннотированным тегом, зарегистрировать незавершённый выпуск.
5. Собрать и сохранить кандидат в GHCR. Если кандидат уже сохранён, продолжать с его digest.
6. Проверить все CLI на обеих архитектурах, выполнить сканирование и сохранить отчёты, provenance, SBOM и attestation.
7. Назначить итоговые теги проверенному digest, сверить результат и отметить выпуск завершённым.

При сбое выпуск остаётся незавершённым. Успешные внешние действия проверяются перед повтором; новый номер не создаётся. После ручной отмены возобновление отменённого выпуска запрещено.

## Исходное состояние

- Версии закреплены в Dockerfile через `CODEX_VERSION`, `OPENCODE_VERSION` и `CLAUDE_CODE_VERSION`.
- Инструменты устанавливаются из npm: `@openai/codex`, `opencode-ai`, `@anthropic-ai/claude-code`.
- Версия образа хранится отдельно в `VERSION`.
- `.github/workflows/build-push.yml` собирает и публикует образы для AMD64 и ARM64 по тегам `v*.*.*` и через `workflow_dispatch`.
- `task release` допускает изменение только `VERSION`, поэтому изменение Dockerfile нужно коммитить отдельно либо реализовать общий release-коммит в workflow.

## Ограничения реализации

- Пуш тега с `GITHUB_TOKEN` не запускает другой workflow по событию `push`. Нужен явный `workflow_dispatch`; дополнительный PAT для него не требуется.
- При запуске публикации передавать именно release-тег, чтобы checkout и Docker metadata относились к выпускаемой версии.
- Проверить правила защиты основной ветки; схема записи изменений должна сохранять согласованную полную автоматизацию допустимых обновлений без обхода правил защиты.
- Не менять закреплённые версии остальных зависимостей в рамках этой задачи.
- Расписание GitHub Actions работает на основной ветке и допускает задержки.

## Спецификация реализации

### Границы задачи

Результат реализации — автоматический цикл обнаружения обновлений, резервирования выпуска, проверки кандидата и публикации с восстановлением после сбоев. Подготовка этой спецификации не включает запуск автоматизации или выпуск образа. Задача остаётся активной до реализации и выполнения критериев приёмки.

Изменяются workflow обновления и публикации, добавляются вспомогательные скрипты и проверки, дополняется README. Автоматизация изменяет только три согласованных `ARG` в Dockerfile и `VERSION`; остальные зависимости не обновляет целенаправленно. Перевод всех зависимостей на воспроизводимую сборку, автоматическое принятие major и автоматическое исправление уязвимостей находятся вне задачи.

### Входы и команды

| Вход | Контракт |
| --- | --- |
| Расписание | `17 * * * *`; каждый запуск сначала восстанавливает состояние. Точное время исполнения не гарантируется. |
| Ручная проверка | `operation=check`; тот же порядок обработки, что у расписания. |
| Ручной повтор | `operation=resume`, обязательный `release_id=vX.Y.Z`; продолжить только существующий выпуск. |
| Ручная отмена | `operation=cancel`, обязательные `release_id` и непустая причина; записать автора и время. |
| Публикация | Принимать точный release-тег; сверять SHA тега, `VERSION` и запись выпуска до любых изменений GHCR. |

Неизвестная операция, ветка вместо release-тега, отсутствующий выпуск или несовпадающий SHA приводят к ошибке без изменений. Повтор завершённого выпуска только проверяет результат; повтор отменённого отклоняется. Повторная отмена отменённого выпуска ничего не меняет; отмена завершённого отклоняется.

Обычный цикл замечает принятые изменения Dockerfile на основной ветке не позднее следующего успешно выполненного почасового запуска. Немедленный запуск после merge не обязателен. Если до проверки принято несколько PR, выпускается актуальный состав Dockerfile основной ветки без подстановки npm-обновлений; промежуточные составы не образуют очередь отдельных релизов.

Ручной `task release` и событие `push` release-тега должны входить в тот же протокол публикации: уже выбранный номер повторно не увеличивается. Ручная публикация из произвольной ветки не должна назначать release-теги или обходить проверки. Если сохраняется отдельная диагностическая сборка ветки, она публикует только служебные теги.

### Выбор версий

| CLI | npm-пакет | ARG | Команда проверки |
| --- | --- | --- | --- |
| Codex | `@openai/codex` | `CODEX_VERSION` | `codex --version` |
| OpenCode | `opencode-ai` | `OPENCODE_VERSION` | `opencode --version` |
| Claude Code | `@anthropic-ai/claude-code` | `CLAUDE_CODE_VERSION` | `claude --version` |

1. Читать основной Dockerfile; каждый целевой `ARG` должен встретиться ровно один раз и содержать стабильную SemVer-версию без префикса `v`, prerelease или build metadata. `VERSION` должен содержать одну такую версию.
2. Получить и полностью проверить ответы всех трёх npm-пакетов до изменения файлов. Сетевая ошибка, неполный ответ или некорректный `latest` останавливают цикл без частичного обновления.
3. Из списка опубликованных версий исключить prerelease и build metadata; версии сравнивать численно по тройке major/minor/patch. Нестабильные версии в списке нормальны; структурно повреждённый ответ является ошибкой.
4. Для каждого CLI выбрать максимальную стабильную версию в текущем major, только если она больше закреплённой. По согласованной политике это правило действует и для major `0`.
5. Если стабильный `latest` имеет больший major, зарегистрировать уведомление с ключом `major:<package>:<major>`. Искать существующую Issue среди открытых и закрытых; закрытие не разрешает обновление и не вызывает создание дубля.
6. Объединить допустимые изменения в один выпуск. Если они отсутствуют, не создавать release-коммит, тег или сборку. Уведомление о major само по себе не является выпуском.

Ошибка чтения npm не мешает продолжению уже начатого выпуска или выпуску принятого ручного состава: эти пути не зависят от новых ответов registry.

### Идентичность состава и начальная настройка

Для распознавания ручных изменений и отменённых составов использовать `composition_id`: SHA-256 точного содержимого Dockerfile. Изменение Dockerfile при прежних версиях CLI создаёт другой состав; изменение README, workflow или `VERSION` — нет. При автоматическом обновлении вычислять идентификатор после подстановки выбранных версий.

Хранить последний завершённый состав и множество отменённых составов. Перед резервированием сравнивать с ними итоговый состав: отменённый состав не резервируется повторно даже при совпадении результата новой npm-проверки. Новый допустимый состав может получить следующий номер.

При первом включении явно зарегистрировать базовый выпуск: версия, release-тег, SHA, состав и существующий digest образа. Проверить их соответствие; не выбирать базовый выпуск по времени изменения `latest`. Если подтвердить соответствие нельзя, остановить включение с диагностикой. Исторические теги до базового выпуска не считать незавершёнными. Базовый выпуск обозначить как импортированный, не приписывая ему новые проверки.

### Долговечное состояние

Предлагаемый вариант — отдельная служебная Git-ветка `release-state` с записями JSON; перед реализацией проверить её совместимость с правилами репозитория. Она хранит состояние, а GHCR — кандидаты. Отчёты должны сохраняться долговечно, например как assets GitHub Release; Actions artifacts допустимы только как дополнительная копия. Конкретный формат хранения отчётов требуется закрепить до реализации публикации.

Минимальная запись выпуска:

| Поля | Назначение |
| --- | --- |
| `schema_version`, `release_id`, `image_version` | Версия схемы и уникальная идентичность выпуска. |
| `source_sha`, `release_sha`, `git_tag`, `composition_id` | Исходная ревизия, закреплённые исходники и состав. |
| `origin`, `previous_versions`, `expected_versions` | Причина выпуска: npm, ручной состав или ручной тег; версии трёх CLI. |
| `status`, `candidate_tag`, `candidate_digest`, `platform_digests` | Этап и идентичность полного кандидата и обеих архитектур. |
| `checks`, `reports`, `attestation` | Результаты по архитектурам, ссылки и контрольные суммы отчётов, подтверждение provenance/SBOM. |
| `attempts`, `failure_count`, `last_error`, `failure_issue` | Уникальные попытки, число неудач и уведомление. |
| `published_tags`, `created_at`, `completed_at`, `cancellation` | Проверенные назначения тегов, время и сведения об отмене. |

Для каждой попытки сохранять уникальный идентификатор запуска и результат. Не учитывать одну неудачу повторно при восстановлении. Прерванный запуск считается неудачной попыткой после подтверждения, что он больше не выполняется; пропуск из-за занятого исполнителя не считается неудачей. После третьей неудачи создать Issue с ключом `release-failure:<release_id>`; при сбое создания повторять уведомление, не прекращая восстановление выпуска.

Обновлять состояние с проверкой ожидаемой предыдущей ревизии, без force push. Неизвестная схема, конфликт идентичности или несколько активных выпусков останавливают мутации с диагностикой. Потеря хранилища не трактуется как отсутствие выпусков и не разрешает новый бамп.

### Состояния и переходы

| Состояние | Условие перехода дальше |
| --- | --- |
| `reserved` | Номер, release-коммит и аннотированный тег закреплены; линтер прошёл; полный кандидат сохранён в GHCR. |
| `candidate_saved` | Проверены версии всех CLI на обеих архитектурах; сканы и отчёты сохранены; provenance, SBOM и attestation доступны для данного digest. |
| `verified` | Повторно проверена отмена; начато назначение итоговых тегов. |
| `publishing` | Все требуемые теги сверены с digest кандидата с учётом защиты общих тегов от отката. |
| `completed` | Терминальное состояние; пересборка и повторный бамп запрещены. |
| `cancelled` | Терминальное состояние; продолжение запрещено, номер и кандидат сохранены. |

Ошибка сохраняет последний подтверждённый этап и причину. Проверки внутри этапа имеют отдельные результаты, чтобы повторять только необходимые действия. Успех нельзя записать до проверки внешнего результата.

Резервирование автоматического выпуска должно атомарно отправлять изменения основной ветки, новый тег и первоначальную запись состояния. При несовпадении ожидаемого HEAD отправка целиком отклоняется; следующий запуск заново читает основную ветку. Если выбранное хранилище не позволяет общую атомарную операцию, реализация обязана сначала закрепить долговечное намерение и доказать восстановление всех промежуточных состояний отдельными тестами.

Для внешнего ручного тега первоначальная регистрация выполняется при обработке события или очередном восстановлении. Тег обязан однозначно соответствовать `VERSION`; конфликт с другим активным выпуском блокирует публикацию и требует диагностики. Существующий номер и тег никогда не перезаписываются.

### Кандидат, проверки и итоговые теги

Служебный тег кандидата: `candidate-vX.Y.Z`. До его появления разрешены повторы сборки release-SHA. После появления полного многоархитектурного индекса проверить его связь с выпуском, сохранить digest и использовать только ссылки по digest. Если push завершился, но запись состояния не сохранилась, следующий запуск сначала ищет и сверяет кандидат, а не начинает новую сборку.

Проверка готовности кандидата требует `linux/amd64` и `linux/arm64`; одних отдельных платформенных образов недостаточно. Все шесть проверок CLI запускаются с явной платформой и entrypoint из таблицы, конечным таймаутом и проверкой exit code. Версия извлекается из вывода соответствующего CLI и сравнивается точно; совпадение произвольной подстроки не считается успехом. Нужны проверки всех трёх CLI, включая неизменившиеся.

Сканировать обе платформы по их digest. Находки HIGH/CRITICAL сохранять в отчёте; они не блокируют выпуск. Ошибки получения базы, запуска сканера, разбора или сохранения отчёта блокируют переход. Не использовать общее подавление ошибок сканирования. Сохранить существующие provenance, SBOM и загрузку SARIF; ошибка обязательной загрузки отчёта тоже блокирует выпуск.

Итоговые теги: `X.Y.Z`, `X.Y`, `X`, `latest` и существующие короткий/полный SHA-теги. Точный semver-тег и SHA-теги не должны менять ранее опубликованный digest. При конфликте сообщить об ошибке. Общий тег назначается только если выпуск новее уже назначенного ему по SemVer; для `X.Y` и `X` сравнение выполняется внутри соответствующей линии. Неизвестное происхождение текущего общего тега требует диагностики, а не слепой перезаписи.

Назначение тегов — копирование сохранённого индекса без пересборки и изменения manifest. После каждого назначения сверять digest. Нельзя считать несколько обновлений тегов атомарной операцией: при частичном успехе записать подтверждённые назначения и продолжить остальные при повторе.

### Сериализация и отмена

Все пути изменения выпусков, включая ручной тег, повтор и отмену, используют один протокол взаимного исключения. Вызывающий workflow не ждёт дочерний, удерживая ту же блокировку. Очередь GitHub Actions не является долговечным хранилищем работы: почасовой запуск должен восстановить пропущенную обработку из сохранённого состояния.

Отмена действует с момента её записи в состоянии. Проверка отмены и назначение каждого итогового тега сериализуются с записью отмены. Если публикация успела завершиться до применения команды отмены, команда возвращает «выпуск завершён». Если назначена лишь часть тегов, отмена запрещает дальнейшие назначения, сохраняет уже назначенные теги и отражает частичную публикацию в summary. Отмена запуска Actions сама по себе не отменяет выпуск.

### Восстановление после внешних действий

| Место сбоя | Поведение следующей попытки |
| --- | --- |
| До резервирования | Прочитать актуальный HEAD и заново вычислить изменения. |
| После отправки release-тега, до dispatch | Найти зарегистрированный выпуск и явно запустить продолжение без бампа. |
| После dispatch, до записи результата | Проверить состояние/активный запуск; дублирующий вызов не создаёт второй кандидат. |
| Во время сборки до готового индекса | Повторить сборку тех же исходников. |
| После сохранения кандидата, до записи digest | Найти служебный тег, проверить индекс и принадлежность выпуску, восстановить digest. |
| После успешной проверки или загрузки отчёта | Проверить подтверждение и повторно использовать результат, привязанный к digest. |
| После части итоговых тегов | Сверить registry и назначить оставшиеся разрешённые теги без отката более новых. |
| После всех тегов, до `completed` | Сверить проверки, отчёты и теги, затем завершить выпуск без сборки. |
| Кандидат исчез или служебный тег указывает на другой digest | Сообщить об ошибке; не менять сохранённый digest и не пересобирать. |
| Issue создана, но её номер не записан | Найти её по устойчивому ключу среди открытых и закрытых, сохранить номер. |

### План проверки реализации

Проверить чистую логику выбора версий, переходов состояния и планирования тегов на фиксированных данных без обращения к npm/GHCR. Интеграционные сценарии должны моделировать сбои между внешним действием и сохранением состояния. Проверка только успешного пути недостаточна.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Нет обновлений | Нет release-коммита, тега и сборки. |
| Один или три CLI обновились | Изменены нужные ARG; patch образа увеличен один раз. |
| `1.9.0` и `1.10.0` | Выбрана `1.10.0`, сравнение не лексикографическое. |
| `latest=2.0.0`, текущая `1.8.0`, доступна `1.9.1` | Выпускается `1.9.1`; одна Issue о major 2. |
| Prerelease в списке или более старый latest | Нестабильные кандидаты игнорируются; отката нет. |
| Ошибка одного npm-ответа | Нет частичного изменения остальных CLI. |
| Принят PR и одновременно появилась новая npm-версия | Сначала выпускается состав основной ветки, npm — следующим циклом. |
| Любая из шести проверок CLI не прошла | Итоговые теги не назначаются. |
| Уязвимости / техническая ошибка Trivy | В первом случае выпуск продолжается с отчётом, во втором — приостанавливается. |
| Две конкурентные проверки / изменение HEAD | Нет второго бампа, force push или устаревшего release-тега. |
| Три неудачи и повтор сбоя создания Issue | Одна Issue на выпуск; повторные попытки продолжаются. |
| Отмена до/во время публикации | Новых назначений после применения отмены нет; существующие сохраняются. |
| Отмена и затем исправление Dockerfile без смены CLI | Исправленный состав допускает новый номер; прежний не повторяется. |
| Каждый сбой из таблицы восстановления | Сохраняются номер, SHA и уже закреплённый digest. |
| Повтор старого завершённого выпуска | Нет сборки и отката `latest`, major или minor. |

Для реальной проверки образа выполнить `task lint`, `task build`, `docker run --rm docker-codex:dev --version`, проверки OpenCode/Claude Code с переопределённым entrypoint и `task scan`. Проверки workflow должны дополнительно подтвердить обе архитектуры, сохранение отчётов/attestation и равенство digest до и после назначения тегов в тестовом пространстве GHCR. В PR записать команды, результаты и ограничения среды; непроведённую проверку не отмечать пройденной.

### Условия готовности к включению

- Подтверждены права записи основной и служебной веток, атомарного резервирования, dispatch, Issues, GHCR, attestation и SARIF. Права выдаются соответствующим jobs; PAT по умолчанию не добавляется.
- Подтверждены импорт базового выпуска и долговечное хранение состояния/отчётов.
- Проверено, что выбранный способ назначения тегов сохраняет исходный многоархитектурный digest вместе с provenance/SBOM; проверка на GHCR обязательна.
- Выполнены сценарии восстановления и отмены, обновлён README с параметрами команд и значением статусов.
- Только после реализации и приёмки статус задачи меняется на завершённый, а каталог переносится в `docs/tasks/completed/`.

## Критерии приёмки

- [ ] Без новых версий и незавершённых выпусков workflow не меняет файлы репозитория и не запускает публикацию.
- [ ] Обновление любого одного CLI корректно меняет соответствующий `ARG` и patch-версию образа.
- [ ] Одновременное обновление нескольких CLI создаёт один релиз.
- [ ] Major-обновление CLI не устанавливается автоматически и поступает на ручное рассмотрение.
- [ ] Уведомление о новом major не дублируется; допустимые обновления других CLI и текущего major продолжают обрабатываться.
- [ ] Prerelease, некорректный ответ или ошибка npm не приводят к частичному обновлению и выпуску.
- [ ] Более старая версия в канале `latest` не вызывает откат.
- [ ] Ошибка сборки или проверки запуска CLI на любой из двух архитектур блокирует публикацию итоговых тегов.
- [ ] Находки сканера включаются в отчёт и не блокируют выпуск; техническая ошибка сканирования или сохранения отчёта приостанавливает выпуск до успешного повтора.
- [ ] Успешный выпуск публикует AMD64/ARM64-образ с semver-тегами, соответствующими `VERSION`, и сохраняет существующие provenance, SBOM и Trivy-проверки.
- [ ] Повторный запуск и конкуренция не создают дублирующие релизы и не перезаписывают git-теги.
- [ ] Частичный сбой автоматически восстанавливается без нового бампа; до завершения выпуска следующий автоматический релиз не начинается.
- [ ] Сохранённый кандидат повторно используется по тому же digest без пересборки.
- [ ] После трёх неудачных попыток одного выпуска создаётся ровно одна Issue; повторы продолжаются каждый час.
- [ ] Слияние PR с принятой major-версией запускает автоматический выпуск, даже если npm не содержит более новой допустимой версии.
- [ ] Из принятого PR выпускается точный состав; появившееся обновление npm обрабатывается следующим циклом.
- [ ] Ручная отмена прекращает повторы конкретного выпуска, не переиспользует номер и допускает новый выпуск исправленного состава.
- [ ] Сбой после отправки git-тега, сохранения кандидата или частичного назначения итоговых тегов восстанавливается без нового бампа и без подмены digest.
- [ ] Повтор завершённого выпуска не запускает новую сборку; повтор старого выпуска не откатывает общие теги образа.
- [ ] Потеря сохранённого кандидата не приводит к его автоматической замене другим digest.
- [ ] Результаты проверки workflow и сценариев обновления задокументированы в PR.
