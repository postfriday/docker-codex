# Продолжать выпуск с тем же digest кандидата

Повторная сборка того же git-тега может изменить состав docker-codex из-за незакреплённых зависимостей. Поэтому собранный кандидат сохраняется в GHCR под служебным тегом, а повторные попытки выпуска используют тот же digest вместо пересборки: опубликован должен быть именно проверенный образ.

Это требует сохранять доступность кандидата до завершения выпуска. Если неисправен сам кандидат, повтор проверки не исправит его: предусмотрена ручная отмена выпуска с сохранением использованного номера и кандидата для диагностики, после которой исправленный состав выпускается под новым номером.


Связанные документы: [спецификация](task.md), [термины](context.md).

## Резервировать номер до сборки

Release-коммит и аннотированный тег закрепляют исходники до сборки, поэтому неудачная попытка может оставить номер без готового образа. Принимаем этот разрыв ради однозначного восстановления: номер не переиспользуется, а доступность выпуска определяется завершением проверок и публикации, а не существованием git-тега.

## Хранить состояние отдельно от запусков Actions

В реализации журнал выпусков хранится в служебной Git-ветке `release-state`, а кандидаты — в GHCR: история запусков, cache и временные artifacts не обеспечивают требуемого долговечного восстановления. Атомарное резервирование проверено на локальном bare Git-репозитории; серверные права записи остаются условием включения. Это добавляет сопровождение состояния и отчётов, но позволяет восстановить выпуск после потери локальных результатов job.


## Хранить отчёты в GitHub Release assets

SARIF обеих архитектур хранится в assets выпуска, первоначально draft. В журнале
сохраняются digest, SHA-256 файла и подтверждение обработки GitHub Security. Это
позволяет пережить удаление Actions artifacts и восстановиться после загрузки файла,
ответ на которую был потерян. Повтор сверяет содержимое; завершение открывает Release.

## Сериализовать workflow целиком

Оба workflow используют одну concurrency-группу. Update отправляет явный dispatch
и завершается, не ожидая Publish под той же блокировкой. Это упрощает сериализацию
отмены с каждым назначением тега; цена — команда отмены ждёт завершения уже работающего
workflow. Долговечная очередь — журнал Git, поскольку Actions может заменить ожидающий
запуск. Отмену конкретного выпуска нельзя подменять отменой запуска Actions.

## Не включать расписание без импорта

`AUTO_RELEASE_ENABLED=true` включает расписание после явного импорта базы и проверки
прав/поведения GitHub и GHCR. Отсутствие журнала — ошибка, а не пустое начальное состояние.
Публичная проверка 2026-09-10 показала `main.protected=false` и пустые branch rules;
это не подтверждает права токена на запись или возможность публикации.

## Сохранить текущие предупреждения линтера

Hadolint запускается с `--failure-threshold error` и выводит все предупреждения.
Текущий Dockerfile содержит предупреждения о pinning apt и стиле; менять остальные
зависимости ради нового pipeline вне согласованного объёма. Ошибки линтера блокируют
сборку. Порог одинаковый в Taskfile и workflow.
