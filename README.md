## Автоматическое обновление CLI

Workflow `Update CLI tools` проверяет npm каждый час (`17 * * * *`, возможны задержки
GitHub Actions). Он принимает стабильные patch/minor в текущем major каждого CLI,
включая major 0. Для следующего major создаётся одна Issue на пакет и major, даже
если предыдущую Issue закрыли. Принятие major — обычный PR с изменением ARG в
Dockerfile. Сначала выпускается точный состав основной ветки, затем рассматриваются
новые версии npm. Несколько обновлений получают одну новую patch-версию образа.

Расписание начинает работу только после установки repository variable
`AUTO_RELEASE_ENABLED=true`. До этого доступны ручные проверки. Первичная настройка:

1. Слить workflow и скрипты в основную ветку. Проверить разрешения Actions и правила
   веток `main` и `release-state`. Инициализация читает серверные rulesets и откажется
   при обнаружении защиты: способ совместимой интеграции нужно согласовать отдельно.
   Правила защиты не обходятся; PAT не требуется.
2. В `Update CLI tools` выбрать `operation=initialize`, передать точный существующий
   аннотированный `release_id=vX.Y.Z` и `baseline_digest=sha256:…`. Проверяются VERSION,
   SHA, OCI-метки, semver-тег и обе архитектуры существующего образа. База получает
   статус `imported`: новые проверки ей не приписываются. `latest` не используется
   для выбора базы. Повторный импорт и потеря ветки состояния — ошибки.
3. В тестовом репозитории/GHCR проверить права записи, atomic push трёх refs, dispatch,
   Issues, загрузку SARIF, attestation, отчёты и сохранение digest при назначении тегов.
   Затем выполнить ручной `check` и включить `AUTO_RELEASE_ENABLED`.

Команды с GitHub CLI (заменить номер выпуска):

```sh
gh workflow run update-tools.yml -f operation=check
gh workflow run update-tools.yml -f operation=resume -f release_id=v1.0.21
gh workflow run update-tools.yml -f operation=cancel -f release_id=v1.0.21 -f reason='Ошибка в рецепте установки'
gh workflow run build-push.yml --ref v1.0.21 -f release_id=v1.0.21
```

`resume` требует существующей записи. `build-push.yml` также регистрирует внешний
аннотированный тег, если он соответствует VERSION, принадлежит истории основной
ветки и не конфликтует с активным выпуском. Почасовая проверка восстанавливает
пропущенные события тегов; несколько незарегистрированных новых тегов требуют
диагностики. `task release PUSH=true` отправляет ветку и тег атомарно. Ветка вместо
номера выпуска не принимается. Публикация запускается на самом release-теге
(`--ref vX.Y.Z`); запуск из ветки отклоняется до изменения состояния. Координатор берётся из основной ветки, а Dockerfile
и контекст сборки — из проверенного release-SHA.

## Состояние, проверки и повторы

Журнал `state.json` хранится в отдельной ветке `release-state`, без force push.
Release-коммит, аннотированный тег и запись журнала отправляются одной атомарной
операцией. Git-тег резервирует номер, но ещё не означает публикацию образа.
Оба workflow используют общую concurrency-группу с `cancel-in-progress: false`;
вызывающий workflow отправляет dispatch и освобождает блокировку, не ожидая сборку.
Потерянный dispatch восстанавливается по журналу следующим почасовым запуском.

Статусы: `reserved` → `candidate_saved` → `verified` → `publishing` → `completed`.
`cancelled` прекращает выпуск; `imported` обозначает базовый исторический образ.
Сначала продолжается незавершённый выпуск, поэтому следующий номер не резервируется
до его завершения или отмены. Отмена исполняется под той же блокировкой и может ждать
окончания текущего workflow. Прерывание Actions само по себе не отменяет выпуск.
После трёх неудач создаётся одна Issue; ошибка уведомления не прекращает повторы.

Кандидат сохраняется как `ghcr.io/postfriday/docker-codex:candidate-vX.Y.Z`.
После появления полного индекса он проверяется и закрепляется по digest. Исчезновение
или изменение кандидата блокирует продолжение; автоматической пересборки сохранённого
кандидата нет. Не удаляйте служебные теги и ветку состояния; сохраняйте резервные копии.
Исправление Dockerfile после отмены допускает новый номер даже при прежних версиях CLI.
Отменённый состав и использованный номер повторно не применяются.

Перед итоговыми тегами выполняются Hadolint, шесть проверок CLI `--version` с явными
entrypoint/платформами и таймаутом, Trivy для каждого платформенного digest, проверки
BuildKit provenance/SBOM и GitHub attestation. Hadolint блокирует ошибки; существующие
предупреждения о незакреплённых apt-пакетах и стиле остаются видимыми. Закрепление
остальных зависимостей не входит в эту задачу. Trivy HIGH/CRITICAL не блокируют выпуск,
но технические ошибки сканирования, некорректный SARIF и ошибки загрузки блокируют его.

Отчёты `trivy-amd64.sarif` и `trivy-arm64.sarif` сохраняются как assets GitHub Release
(до завершения — draft); журнал хранит контрольные суммы и результаты загрузки в
GitHub Security. При повторе отчёты скачиваются и сверяются. Actions artifacts/cache
не являются хранилищем состояния. Публикуются `X.Y.Z`, `X.Y`, `X`, `latest`, короткий
(7 символов) и полный SHA. Индекс копируется без пересборки с проверкой digest после
каждого назначения. Неизменяемые теги не перезаписываются, общие теги не откатываются;
неизвестный владелец общего тега вызывает ошибку. Отмена сохраняет уже назначенные теги.

Update job получает `contents: write`, `actions: write`, `issues: write`, `packages: read`.
Publish job получает `contents: write` (журнал и assets), `packages: write`, `issues: write`,
`actions: read`, `id-token: write`, `attestations: write`, `security-events: write`.
Права GHCR, attestation и Code Scanning должны поддерживаться настройками репозитория.

Локальная проверка логики без сети: `task test`. Workflow проверяются `actionlint`.
Состояние реализации и ограничения реальной проверки описаны в
[задаче 1](docs/tasks/0000000001-auto-update-tools/task.md).
